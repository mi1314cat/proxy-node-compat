## 1 · 「原本」和「现在」分别是什么

### 1.1 关键区别：**分享出去的是什么格式**

| 内核 | **互通前（原本）** token 发的 | **互通后（现在）** token 发的 |
|---|---|---|
| **SB** | **sing-box JSON**（自家原生，跨生态读不了） | **普通话 URI 列表（主）** + sing-box JSON（附带）+ 地址上带声明 |
| **M** | **mihomo `proxies:` YAML**（自家原生，跨生态读不了） | **普通话 URI 列表（主）** + mihomo YAML（附带）+ 声明 |
| **X** | **base64 的订阅行 = 本来就是普通话** | 普通话（主）+ xray 原生（附带）+ 声明 |

> **X 的特殊性（有据）**：X 互通前的 `conf/lib/share_payload.py` 文件头就写着
> "★ 载荷格式一字未改: base64 的订阅行。已发出去的链接、已经导入过的客户端都按这个格式解析"。
> 所以 **X 的主产品形态从来没变**，互通只给它加了声明和原生附带。
> **需要"退回原状"的主要是 SB 和 M** —— 这也是用户的原话。

### 1.2 两个版本在哪（都在 GitHub 上，随时可取）

| 内核 | 「原本那版」 | 「现在这版」 | 两者关系 |
|---|---|---|---|
| SB | tag **`pre-three-way-interop`** → `c0a5c19` | `main` → `b25f5a0` | 相隔 19 个提交 |
| M | tag **`pre-three-way-interop`** → `32c03d7` | `refactor/v2` → `01890ef`（= `origin/main`） | 相隔 14 个提交 |
| X | tag **`pre-three-way-interop`** → `7dfe2a5` | `main` → `957e603` | 相隔 32 个提交 |

> 三个回退点**都是 `origin/main` 的祖先** —— 任何 clone 都能 `git checkout` 到，
> **不需要额外备份**。本地还额外打了 annotated tag（**未 push**，要上 GitHub 就
> `git push origin pre-three-way-interop`）。RN 上另有冻结快照 `/root/catmi/_versions/`
> （详见 `pre-interop-rollback-points.md` §8）。

### 1.3 「回到原状」到底意味着什么（三个层面，别混）

| 层面 | 原本 | 现在 | 退回去要动什么 |
|---|---|---|---|
| **A. 分享载荷格式** | 只发原生 | 普通话主 + 原生附带 | 服务端 `share.sh` 的建分享逻辑 |
| **B. 地址上的声明** | 没有 | `?interop=1&kernel=…&formats=…` | 同上 + 地址拼装 |
| **C. 客户端行为** | 当普通订阅解析 | 先读声明 → 决定拉原生还是普通话 → 失败回退 | 客户端 `client.sh` + `to_sb.py` |

**三件事可以分开退**。只想退 A+B（服务端不发声明、不发普通话）而保留 C 是无害的
（客户端读到"没有声明"就走普通话，日志会写"地址上没有内核声明"）。

## 3 · 为什么"整段回退"和"挑修复"都不好用（实测，不是推测）

### 3.1 直接退到回退点 = 丢掉上面全部真修复
`git reset --hard c0a5c19` 会让 SB 丢掉 `45fd108`（**TLS 静默降级**那条）和 `e861ab7`（静默丢节点）——
这两条是**线上真事故的根因修复**。M 同理（丢 SNI 重建修复、"导入成功"假象修复）。

### 3.2 从回退点"挑拣修复"上去：**实测大面积冲突**

我在**一次性 clone**（不碰真仓库）里做了试挑，起点分别为 `c0a5c19`（SB）/ `32c03d7`（M）：

| 内核 | 试挑的非互通修复 | 结果 |
|---|---|---|
| **SB** | `4fccbc6` `fe47df8` `406afcc` `45fd108` `ba1e670` `e861ab7` | **✓1 干净 / ✗5 冲突** |
| **M** | `1c23d1b` `4b09b7e` `23fe60f` | **✓2 干净 / ✗1 冲突** |

冲突原样（SB 挑 `45fd108` 时）：

```
CONFLICT (content): Merge conflict in src/client/to_sb.py
CONFLICT (modify/delete): tools/check_compat_wiring.sh deleted in HEAD and modified in 45fd108 …
```

**根因**：这些修复是在**互通提交之后**做的，文件里已经有了兼容层/声明的上下文；
把它们的补丁硬贴到"互通前"的文件上，上下文对不上。外加它们还改了互通才引入的门禁文件
（`check_compat_wiring.sh`），在回退点上根本不存在。

> **结论**：方案 A（回到基线 + 挑修复）**不现实**，除非你愿意逐个手工解冲突（5 个）。
> 想"保留修复"，就得**从当前版往回摘互通**（方案 B），或者**干脆不摘、加开关**（方案 0）。

## 4 · 现成的回退开关（**不改代码**就能退掉的那一半）

系统里**已经内置**了兼容层的一键回滚（写代码时就留了）：

| 内核 | 开关 | 位置 | 效果 |
|---|---|---|---|
| **SB** | `SB_COMPAT_ENGINE=legacy` 或 `SB_COMPAT_DISABLE=1` | `src/client/to_sb.py:660-663`（`compat_enabled()`） | 兼容判定**整条走旧路径**；compat2 缺失/异常也会自动落回 |
| **M** | `MH_COMPAT_ENGINE=legacy` 或 `XBD_COMPAT_ENGINE=legacy` | `src/lib/nodecompat.py:78` | 同上，整条链路退回客户端原有判定 |

**⚠ 但它只能退一半**：这两个开关关掉的是**"节点能不能用"的判定层**，
**关不掉**下面这三样（这才是"分享格式"的主体）：

1. 服务端**在地址上写声明**；
2. 服务端**产出两条产品**（普通话主 + 原生附带）；
3. 客户端**读声明决定拉原生还是普通话**（`_sb_interop_decide`，SB 在 `client.sh:1179`）。

我 grep 过三家：**这三样没有任何环境变量开关**（`SB_INTEROP_DISABLE` 之类不存在）。

## 5 · 三条可选路线（含推荐）

### ✅ 方案 0（**推荐**）：在当前版上加一个"原状模式"开关

**思路**：不删任何文件、不回退任何提交，只加一个开关，行为上回到原状。

```
SB_INTEROP_MODE=legacy（或 off）
  ├─ 服务端 create_share：
  │    只建"原生"那一条分享记录（内容和 TTL/次数照旧），
  │    不建普通话主记录、地址不带声明 → 分享格式 = 原本
  └─ 客户端 add_node：
       跳过 _sb_interop_decide，直接把取回的正文当普通订阅解析 → 客户端 = 原本
```

- **优点**：改动小且**只增不减**（不动现有路径，默认行为不变）；**一行环境变量就能来回切**；
  **一条真修复都不会丢**；风险低、可随时删掉这个开关。
- **代价**：代码里仍留着互通实现（**"臃肿"没解决**）；门禁要加"legacy 模式下行为等于原状"的断言。
- **适合**：你现在的心态 —— "能用，先这么用；哪天想退，一条命令就退"。

### 方案 B：从当前版**手工摘掉互通**（保留全部修复）

- 按 §6 的逐文件清单删函数、改 `create_share`/`add_node`。
- **优点**：代码真的回到"只有原本那套"，臃肿消除。
- **代价**：**外科手术**，共享文件里互通与非互通的代码**交织**（§6.3 列了交织点），
  预计 1~2 天 + 完整回归（分享、订阅、四道闸门、客户端导入、对角线）。
- **适合**：确定以后不再要互通，且愿意投入时间。

### 方案 C：回到回退点 + 手工补 5 个修复

- **优点**：历史干净（就是"原本那版 + 几个修复"）。
- **代价**：**最贵** —— 5 个冲突要手工解，且要重新补门禁文件；`ba1e670`/`e861ab7` 这种
  改动面较大的还得重新验证。
- **只在**你确定要"一条干净的历史线"时才选。

## 8 · 风险与陷阱（会咬人的地方）

1. **`e99f2ba` 不是 M 的回退点** —— 它前面还有 9 个提交含真修复（§2.2 的坑）。
2. **`check_share_links.sh` / `check_compat_wiring.sh` / `interop-e2e.sh` 这些门禁**
   本身就是互通带来的，删互通时它们要么删、要么改成不含互通断言 ——
   **别把它们留成"永远红"的状态**，否则以后没人看门禁。
3. **`install.sh` 的 `install_server_compat()`** 是"互通引入的 bug 的修复"
   （不装 `compat2`+`lib` 会导致**整个分享功能不可用**）。删互通时要连它一起删，
   但**删完必须确认分享还能建**（§7 服务端第一条）。
4. **发布闸门 vs 通用校验别搞混**：`link_guard`/`uri_express` 是互通闸门（可删）；
   `sb_share_consistency_check`（端口/节点存在性）是**通用**的（保留）。
5. **客户端三处"看得见的失败"是 `e861ab7`/`ba1e670` 加的，不是互通**：
   `转换器跳过了 N 条`、read-EOF 的报错、`URI 协议未收录`。
   它们的价值是"少节点时你能发现" —— **删了这些，静默丢节点就回来了**。
6. **`tools/check_compat_wiring.sh` 跑一次要 60s+**，脚本化调用别用 60s 硬超时（会误判失败）。
7. **X 的 `conf/lib/share_payload.py` 里那段 base64 是原本就有的**（文件头写着"载荷格式一字未改"），
   **不要因为"它长得像互通"就删**。
