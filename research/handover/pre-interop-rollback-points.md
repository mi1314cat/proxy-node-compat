## 3 · 回退之后会变成什么样（准确描述，避免预期错位）

以 SB 为例，`c0a5c19` 那一版的分享形态（实测该提交的代码）：

- **分享 token 发的是一份内容**：`out/sb_client-<tag>.json` —— **原生 sing-box JSON**，就一种。
- **每一行的 URI 链接产物其实早就有**：`sb_share-<tag>.txt` 与聚合的 `sb_links-all.txt`
  是各协议脚本（`vless.sh` / `vmess.sh` / `hysteria2.sh` …）自己写的，`c0a5c19` 里就在，
  **不是互通带来的**。但它们当时只是**旁路产物**，不是分享 token 发出去的东西。
- 没有的东西：地址上的**内核声明**、**两条产品成对**（普通话主 + 原生附带）、
  发布前的**四道闸门**（链接校验 / URI 表达力标注 / 一致性 / 节点集合一致）、
  客户端侧**读声明决定拉原生还是普通话 + 回退**。

所以准确说法是：

> **"普通话"（URI 列表）作为"分享出去的主产品"是互通带来的；而"生成 URI 链接"这件事本身早就有。**
> 回退到边界 A 之后，SB 的分享回到"只发自家原生 JSON"，
> **mihomo / xray 的客户端拉过去依然是"0 个节点"** —— 那正是 `proxy-node-compat` 当初要解决的问题。
> （你印象里"普通话 = 三端交互前的状态"，从**格式**上讲是对的：URI 列表是最原始、谁都能读的形态；
> 但它在 SB 这条线上**从旁路产物升格为主产品**，是互通做的。）

三个内核同理：**各自只发自己的原生格式**，跨生态读不了 —— 这是边界 A 的全部含义。

## 4 · 真要回退时怎么做（命令 + 风险，先看再动）

三个仓库当前都**没有未推提交**，也就是说 GitHub 上的 `main` 就是现在这一版。
回退有两条路，**风险和可逆性完全不同**：

### 路 1（推荐，不改历史）：**开一个回退分支**

```bash
# 例：SB 回到互通前
cd /root/deepseek/repos/sing-box-core
git checkout -b rollback/pre-interop c0a5c19
git push -u origin rollback/pre-interop      # 只新增分支, 不动 main
```
- 好处：**主分支历史一个字都不改**，随时 `git checkout main` 回来继续用现在的；
  你要"之后哪天内核更新了只改中转项目"时，这个分支就是干净基线。
- 代价：多一个分支；线上要换版本得另外分发（RN/CC 的部署路径）。

### 路 2（不推荐）：把 `main` 指回旧版本
```bash
git checkout main && git reset --hard c0a5c19 && git push --force origin main
```
- **风险**：`--force` 会**改写公开历史**；已经分发到 RN/CC 的部署路径会与新 `main` 不一致；
  而且**回退掉的 8~10 个互通提交里夹着与互通无关的真修复**（见 §1 那条提示）。
- 真要走这条，**先备份当前 `main` 的 sha**，并且**回退后必须重新分发 + 重跑三家门禁**。

> 我**没有**执行以上任何一条 —— 按你的话，现在的工作还会继续用。

## 5 · 关于你的判断："又臃肿又不好用" —— 用数字说话

你的意思是：**原本设想只优化"中转"这一个项目**，之后无论哪个内核更新，
**只动中转那一处就够了**；而现在的做法把跨内核的东西铺进了每个内核仓库。

我把这件事量化了一下（都是当前 HEAD 实测，不是感觉）：

### 5.1 同一份"兼容层"被复制了 4 份

| 位置 | 文件数 | 行数 |
|---|---|---|
| canonical：`proxy-node-compat/proxy_node_compat/` | 8 | 4143 |
| vendored：`sing-box-core/src/client/lib/proxy_node_compat/` | 8 | 4143 |
| vendored：`mihomo--core/src/lib/proxy_node_compat/` | 8 | 4143 |
| vendored：`xray--core/Client/lib/proxy_node_compat/` | 8 | 4143 |

**同一份 4143 行，存在 4 份**（≈16572 行）。为了让它们不漂移，还得在**每个内核仓库各装一道
"逐字节 vs canonical"的门禁** —— 门禁本身也是三份。

### 5.2 同一份"声明契约"被实现了 5 次

| 实现 | 文件 |
|---|---|
| X 服务端 | `xray--core/conf/lib/interop.py`（461 行） |
| X 客户端 | `xray--core/Client/lib/interop.py`（461 行，逐字节副本） |

| SB 客户端 | `sing-box-core/src/client/lib/interop.py`（472 行，逐字节副本） |

**5 份**。这不是我的推断 —— 你上一轮让我跑的
`proxy-node-compat/tools/interop-conformance.py`，正是拿这 5 份来比"零分歧"的。

### 5.3 一次契约改动的**扇出**（这是"臃肿"最硬的证据）

就拿刚做完的"声明缩短（去 version + 同源相对路径）"这一次：

```
X  : 957e603  feat(互通/声明): 地址缩短 …           ← 1 个提交
M  : 47f869e  feat(互通): 收束声明地址 …            ← 1 个提交
SB : b25f5a0  收束: 声明去掉 version + 同源相对路径  ← 1 个提交
```

**一条契约规则，改了 3 个仓库、3 个提交**；每个仓库还各自：
改实现 → 改自己的门禁 → 反向验证 → 重新 vendor（若涉及 canonical）→
分发到 RN/CC → 在部署态复核。**同一条规则写 5 遍、验 3 遍、分发 2 台机器。**
只要漏掉任何一家，跨实现一致性台上就会出现"零分歧"以外的结果。

### 5.4 各内核自带的那套实现（互通新增，非 vendored）

| 内核 | 文件 | 行数 |
|---|---|---|
| SB | `conf/interop.py` 472 + `client/lib/interop.py` 472 + `client/compat2.py` 937 + `conf/link_guard.py` 304 + `conf/uri_express.py` 301 | **2486** |
| M | `src/lib/interop.py` 472 + `src/share/build_uri.py` 498 | **970** |
| X | `conf/lib/interop.py` 461 + `Client/lib/interop.py` 461 + `Client/lib/compat2.py` 811 + `conf/lib/native.py` 492 | **2225** |

### 5.5 结论（对着你的设想说）

- 你的设想：**跨内核这件事收在"中转"一个项目里**，内核仓库只管自己。
- 现在的实际：跨内核这件事**在每个内核仓库里各有一份**（实现 5 处 + 兼容层 4 份 + 门禁 3 道），
  canonical 仓库只解决了"规则表"这一层的单一真源，**协议实现和产品形态仍然是三家各写**。
- 所以"臃肿"不是错觉：**成本不在代码量，在"同一件改动要扇出到 3 个仓库 ×5 份实现"**。
  这也是为什么你觉得"只是做了能用" —— 通路的每一环都得三家同步改一次。

> **要收束成"只改中转"，至少要先定一件事**（现在没定，所以我不动）：
> **声明/决策/两种产品的生成，到底放在"中转项目"里，还是留在各内核？**
> 若放中转：内核只需要暴露"我有哪些节点、选哪个格式"，中转负责声明、配对、闸门、方言适配；
> 三家内核就都不需要 `interop.py` 了。**但这条会改变契约的归属方，属于设计决策，不是收尾动作。**
